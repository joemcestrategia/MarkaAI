PLANS AND BILLING - MarkaAI

Overview
--------
This document describes the subscription plans, included features, billing flow, trial logic, and automation we've implemented for MarkaAI.

Plans (tier names)
- START (free / basic)
  - Core booking features (basic scheduling)
  - Limited notifications
  - Basic reporting (minimal)
  - 1 shop only

- FLEX
  - Everything in START
  - Additional reporting and export
  - Up to 3 shops
  - Priority notifications
  - Monthly price example: R$29.90

- PLUS
  - Everything in FLEX
  - Advanced admin features (CRUD, tags, categories management)
  - Client segmentation (VIP, tags)
  - Advanced reminders & automations
  - Monthly price example: R$69.90

- PRIME
  - Everything in PLUS
  - Enterprise features: white-labeling, analytics, integrations
  - Highest priority support & SLA
  - Monthly price example: R$149.90

Feature mapping (high level)
- User management: all paid plans (search, edit, tags) — admins only
- Shop categories: PLUS and PRIME (but admin can manage categories)
- Tags & VIP: assigned per (user, shop) and usable as filters (PLUS+)
- Notifications: test notifications available in admin (ALL plans, testing)
- Billing & subscriptions: platform-managed (all upgrades paid)

Billing & Trial Flow (automated)
--------------------------------
1) Creating a subscription
   - Endpoint: Cloud Function `createSubscription` (callable).
   - Parameters: userId, shopId (optional), planId, wantTrial (bool).
   - Behavior:
     - If wantTrial = true → subscription.status = 'trialing', trial_end = now + 30 days.
     - Otherwise → subscription.status = 'active' and next_billing = now + 30 days.
     - Subscription document stored in `subscriptions` collection.
     - Audit log written to `admin_audit`.

2) Trial handling (1 month free)
   - Customer can be given a 1-month trial for the selected plan.
   - During trial the customer retains trial features.
   - At trial_end the system attempts to charge automatically if a payment method exists.
   - If no payment method or charge fails → subscription is downgraded to START (or marked past_due). System logs and notifies admin.

3) Automatic recurring billing
   - A daily endpoint `checkSubscriptionsDaily` (Cloud Function HTTP) is deployed.
   - Use Cloud Scheduler to call this endpoint every 24 hours.
   - For subscriptions with next_billing <= now or trial_end <= now, the function:
     - Attempts to charge using stored paymentMethod (if user has one).
     - For charges via MercadoPago, the function will attempt to create a payment using the shop's MercadoPago access token when available.
     - On success: updates next_billing = now + 30 days and logs success.
     - On failure: marks subscription as 'past_due' and logs; optionally notifies admin and can start grace/downgrade logic.
   - If no payment method exists at trial end → immediate downgrade to START (configurable).

4) Payment methods & charging
   - Payment methods are expected to be stored in `users` documents as `paymentMethod` (example structure: { type: 'card', token: 'card_token' }).
   - Charging uses shop's MercadoPago access token (`shops.{shopId}.mercadopago.access_token`).
   - If platform-level charging (using platform MP account) is preferred, adapt the function to use platform credentials.

5) Billing notifications & audit
   - All automated billing actions create audit entries in `admin_audit` and optionally `admin_notifications`.
   - Admins can review and manually intervene.

UX: free trial without CC requirement
------------------------------------
- You requested that the trial not require entering a card.
- Implementation:
  - `createSubscription(..., wantTrial=true)` will create a trial without requiring paymentMethod.
  - Before trial ends, system will try to charge only if a payment method exists.
  - If at trial end there's no payment method, the system downgrades user to START automatically.
  - Optionally: a pre-trial-end email/notification can be scheduled (e.g., 3 days before trial ends) to remind users to add a payment method to avoid downgrade.

Security & Recommendations
--------------------------
- Enable Firestore Security Rules to protect subscription writes (only server/admin functions or specific admin roles).
- Store minimal payment info; use tokens from the payment provider (MercadoPago tokens) — do not store raw card numbers.
- Consider implementing a grace period (e.g., 7 days) before final downgrade.
- Add webhooks from payment provider to reconcile actual payments (preferred for reliability).
